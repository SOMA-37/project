# 05. WBS 및 일정 관리

# 사주 기반 국내 여행지 추천 Agent MVP WBS

## 1. 문서 목적

이 문서는 사주 기반 국내 여행지 추천 Agent MVP의 작업 범위, 담당자, 일정, 완료 기준을 관리하기 위한 WBS 문서입니다.

이번 프로젝트는 AI 3주 프로젝트 과정에서 진행하는 단기 MVP 프로젝트이며, 주요 일정은 다음과 같습니다.

| 구분 | 날짜 | 의미 |
|---|---|---|
| 데모 제출 마감 | 5월 10일 | 동작 가능한 1차 데모 제출 |
| 프로젝트 최종 제출 | 5월 14일 | 코드, 문서, 발표자료 제출 |
| 최종 발표 | 5월 15일 | 최종 발표 및 시연 |

따라서 이번 WBS의 핵심 목표는 다음과 같습니다.

1. 5월 10일까지 최소 동작 데모를 만든다.
2. 5월 14일까지 제출 가능한 형태로 코드와 문서를 정리한다.
3. 5월 15일 발표에서 서비스 정의, Agent Workflow, 시연 결과를 명확히 설명할 수 있게 한다.
4. 팀원별 역할과 완료 기준을 명확히 하여 작업 중복과 누락을 줄인다.
5. 일정이 밀릴 경우 어떤 기능을 줄이고 어떤 기능을 반드시 살릴지 판단 기준을 제공한다.

## 3. 역할별 책임 범위

## 3.1 기획/문서화 담당

담당자:

- 신동운
- 김도훈

주요 책임:

1. 프로젝트 기획 방향 정리
2. MVP 범위 확정

4. Agent Workflow 설계 문서 작성
5. 여행지 데이터 스키마 작성
6. WBS 작성 및 일정 관리

8. 발표 담당자가 이해할 수 있도록 서비스 정의와 시연 흐름 정리
9. 변경사항 발생 시 관련 문서 업데이트

완료 기준:

- 개발팀이 문서만 보고 P0 기능을 구현할 수 있다.
- 발표 담당자가 문서만 보고 서비스 구조와 시연 흐름을 이해할 수 있다.
- 5월 14일 제출 전까지 문서와 실제 구현 내용이 크게 어긋나지 않는다.

## 3.2 개발 담당

담당자:

- 김동건
- 한승우

주요 책임:

1. Streamlit 기반 입력 화면 구현
2. 사용자 입력값 검증 구현
3. 사주 분석 Agent 구현
4. 여행 스타일 매핑 구현
5. 여행지 데이터 로딩 구현
6. 여행지 후보 필터링 구현
7. 추천 점수 계산 구현
8. Top3 추천 결과 선정 구현
9. LLM 추천 이유 생성 구현
10. 결과 카드 화면 출력 구현
11. 예외 상황 처리
12. 데모 제출 가능한 동작 버전 준비

완료 기준:

- 사용자가 입력 폼에 값을 입력할 수 있다.
- 추천 받기 버튼을 누르면 전체 Workflow가 실행된다.
- 추천 여행지 Top3가 결과 화면에 표시된다.
- LLM 호출 실패 또는 후보 부족 상황에서도 앱이 중단되지 않는다.
- 5월 10일 데모 제출이 가능하다.

## 8. 일정 지연 시 대응 기준

일정이 밀릴 경우 다음 기준으로 대응합니다.

## 8.1 절대 줄이면 안 되는 기능

아래 기능은 최종 발표에서 서비스 흐름을 보여주기 위해 반드시 유지합니다.

- 사용자 입력
- 사주 분석
- 여행 스타일 매핑
- 여행지 Top3 추천
- 결과 카드 출력

## 8.2 줄일 수 있는 기능

일정이 부족하면 아래 기능은 축소하거나 제외할 수 있습니다.

| 기능 | 대응 |
|---|---|
| LangGraph 적용 | 함수 기반 Workflow로 대체 |
| LangChain 적용 | 직접 LLM 호출 함수로 대체 |
| 여행지 데이터 30개 | 15개로 축소 |
| 다른 여행지 보기 | 제외 |
| 결과 저장/공유 | 제외 |
| RAG 적용 | 향후 확장으로 설명 |
| 출발 지역 다양화 | 서울 기준 우선 지원 |

## 8.3 일정 지연 공유 기준

아래 상황이 발생하면 즉시 팀원에게 공유합니다.

1. P0 기능 구현이 하루 이상 밀릴 때
2. LLM API 연동이 막힐 때
3. 여행지 데이터가 15개 미만일 때
4. 입력부터 결과 출력까지 전체 흐름이 5월 9일까지 연결되지 않을 때
5. 발표자료와 실제 구현 내용이 달라질 때

공유 방식 예시:

    현재 추천 이유 생성 기능에서 LLM 응답 파싱 문제가 있어 지연되고 있습니다.
    1차 대응으로 기본 템플릿 fallback을 먼저 적용하고,
    시간이 남으면 LLM 응답 형식을 다시 정리하겠습니다.

## 9. 팀 커뮤니케이션 규칙

## 9.1 작업 공유 방식

작업 상황은 가능한 한 짧고 명확하게 공유합니다.

공유 항목:

- 오늘 한 일
- 막힌 부분
- 내일까지 할 일
- 다른 팀원에게 필요한 요청

예시:

    오늘 입력 폼과 여행지 데이터 로딩까지 구현했습니다.
    현재 사주 분석 Agent 프롬프트 응답 형식이 불안정해서 fallback 구조를 추가하려고 합니다.
    내일까지 스타일 매핑과 추천 점수 계산까지 연결하겠습니다.

## 9.2 문서 변경 규칙

문서 변경이 필요한 경우 다음 원칙을 따릅니다.

1. 기능 범위가 바뀌면 기능명세서를 수정한다.
2. Agent 단계가 바뀌면 Agent Workflow 문서를 수정한다.
3. 데이터 필드가 바뀌면 데이터 스키마 문서를 수정한다.
4. 일정이 바뀌면 WBS 문서를 수정한다.
5. 발표 내용이 바뀌면 데모 시나리오 문서를 수정한다.

## 9.3 개발 변경 규칙

개발 중 기능을 바꾸는 경우 다음을 확인합니다.

- P0 기능에 영향을 주는가?
- 데모 제출 일정에 영향을 주는가?
- 문서와 불일치가 생기는가?
- 발표자가 설명하기 어려워지는가?

위 항목에 해당하면 팀원에게 먼저 공유한 뒤 반영합니다.

| 사주 분석 정확도 문제 | 전문 사주 계산이 아님 | 재미와 참고용 면책 문구 표시 |
| 발표와 구현 불일치 | 발표 내용이 실제 기능과 다를 수 있음 | 5/13에 문서와 구현 내용 최종 대조 |
| 일정 지연 | P0 기능 완성이 늦어질 수 있음 | P1 기능 제외, P0 우선 구현 |

## 12. 요약

이번 WBS의 핵심은 다음과 같습니다.

1. 5월 10일까지 동작 가능한 데모를 만든다.
2. 5월 14일까지 코드, 문서, 발표자료를 제출 가능한 상태로 정리한다.
3. 5월 15일 최종 발표에서 서비스 정의, Agent Workflow, 추천 결과를 설명한다.
4. 신동운과 김도훈은 기획/문서화를 담당한다.
5. 김동건과 한승우는 개발을 담당한다.
6. 최근호는 발표를 담당한다.
7. 일정이 밀릴 경우 LangGraph, RAG, 저장/공유 같은 P1 기능을 줄인다.
8. P0 기능인 입력, 분석, 스타일 매핑, Top3 추천, 결과 출력은 반드시 유지한다.

이번 프로젝트는 많은 기능을 구현하는 것이 아니라, 짧은 기간 안에 Agentic AI 기반 추천 흐름을 명확하게 설계하고 동작 가능한 MVP로 보여주는 것이 목표입니다.
