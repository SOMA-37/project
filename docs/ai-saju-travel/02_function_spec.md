# 02. 기능명세서

# 사주 기반 국내 여행지 추천 Agent MVP 기능명세서

## 1. 문서 목적

이 문서는 사주 기반 국내 여행지 추천 Agent MVP의 기능 요구사항을 개발자가 구현할 수 있는 수준으로 정리한 문서입니다.

이번 프로젝트는 5월 10일 데모 제출, 5월 14일 프로젝트 제출, 5월 15일 최종 발표를 목표로 진행합니다.  
따라서 기능명세서는 “상용 서비스 수준의 완성도”보다 “정해진 기간 안에 동작 가능한 MVP 구현”에 초점을 둡니다.

이 문서의 목적은 다음과 같습니다.

1. 사용자가 어떤 정보를 입력해야 하는지 명확히 정의한다.
2. 입력값을 어떤 형태로 시스템에 전달할지 정의한다.
3. 사주 분석 결과를 어떤 여행 스타일로 변환할지 정의한다.
4. 여행지 데이터를 어떤 기준으로 필터링하고 추천할지 정의한다.
5. LLM과 코드 로직의 역할을 구분한다.
6. 개발자가 기능 완료 여부를 판단할 수 있는 기준을 제공한다.
7. 데모 제출에 필요한 P0 기능과 시간이 남으면 구현할 P1 기능을 구분한다.

Agent의 상세 흐름은 03_agent_workflow.md에서 관리합니다.  
여행지 데이터 구조는 04_data_schema.md에서 관리합니다.  
일정과 담당자 관리는 05_wbs.md에서 관리합니다.

## 2. MVP 기능 요약

이번 MVP의 핵심 기능은 다음 한 문장으로 요약할 수 있습니다.

사용자가 생년월일시와 여행 조건을 입력하면, 사주 기반으로 여행 스타일을 분석하고, 여행지 데이터에서 조건에 맞는 국내 여행지 3곳을 추천한 뒤, 추천 이유를 카드 형태로 보여준다.

전체 흐름은 다음과 같습니다.

1. 사용자가 입력 폼에 정보를 입력한다.
2. 시스템이 입력값을 검증한다.
3. 사주 분석 Agent가 입력값을 바탕으로 현재 상태 또는 필요한 기운을 간단히 분석한다.
4. 여행 스타일 매핑 Agent가 분석 결과를 여행 스타일로 변환한다.
5. 여행지 데이터에서 조건에 맞는 후보 여행지를 찾는다.
6. 추천 점수 기준에 따라 후보 여행지를 정렬한다.
7. 상위 3개 여행지를 선정한다.
8. LLM이 각 여행지에 대한 추천 이유를 생성한다.
9. 결과 화면에 여행 스타일, 추천 여행지, 추천 이유, 추천 활동을 카드 형태로 출력한다.
10. 결과 화면에 재미와 참고용 서비스라는 면책 문구를 표시한다.

## 3. 기능 우선순위

## 3.1 P0: 데모 제출 필수 기능

P0 기능은 5월 10일 데모 제출 시점까지 반드시 동작해야 하는 기능입니다.

| 기능 ID | 기능명 | 설명 |
|---|---|---|
| F-001 | 사용자 입력 폼 | 생년월일, 출생 시간, 출발 지역, 여행 조건 입력 |
| F-002 | 입력값 검증 | 필수값 누락 여부 확인 |
| F-003 | 사주 기반 간단 분석 | 입력값 기반으로 현재 상태 또는 필요한 기운 분석 |
| F-004 | 여행 스타일 매핑 | 분석 결과를 여행 스타일 키워드로 변환 |
| F-005 | 여행지 데이터 로딩 | JSON 또는 CSV 기반 여행지 데이터 로딩 |
| F-006 | 여행지 후보 필터링 | 이동 가능 범위, 여행 기간 기준 후보 필터링 |
| F-007 | 추천 점수 계산 | 스타일, 거리, 기간, 선호 태그 기준 점수 계산 |
| F-008 | Top3 여행지 선정 | 점수 상위 3개 여행지 선정 |
| F-009 | 추천 이유 생성 | LLM으로 여행지별 추천 이유 생성 |
| F-010 | 결과 카드 출력 | 추천 결과를 웹 화면에 카드 형태로 출력 |
| F-011 | 면책 문구 출력 | 사주 기반 추천은 재미와 참고용임을 안내 |

## 4. 사용자 입력값 명세

## 4.1 입력값 전체 목록

MVP에서는 자연어 입력보다 선택형 입력을 우선합니다.

선택형 입력을 우선하는 이유는 다음과 같습니다.

1. 구현 난이도를 낮출 수 있다.
2. 입력값 오류를 줄일 수 있다.
3. 추천 기준을 명확하게 만들 수 있다.
4. 여행지 데이터와 매칭하기 쉽다.
5. 데모 상황에서 안정적으로 동작할 가능성이 높다.

| 필드명 | 화면 표시명 | 타입 | 필수 여부 | 예시 | 설명 |
|---|---|---|---|---|---|
| birth_date | 생년월일 | date | 필수 | 1999-03-14 | 사용자의 생년월일 |
| birth_time_branch | 출생 시간 | select | 선택 | 신시 | 12지시 기준 출생 시간 |
| birth_time_unknown | 출생 시간 모름 | boolean | 필수 | false | 출생 시간을 모르는 경우 true |
| calendar_type | 양력/음력 | select | 필수 | 양력 | 생년월일 기준 |
| departure_region | 출발 지역 | select | 필수 | 서울 | 여행 출발 기준 지역 |
| travel_range | 이동 가능 범위 | select | 필수 | 3시간 이내 | 사용자가 이동 가능한 최대 시간 |
| duration | 여행 기간 | select | 필수 | 1박2일 | 당일 또는 1박2일 |
| preference_tags | 선호 태그 | multi-select | 선택 | 바다, 카페 | 사용자가 선호하는 여행 요소 |

## 5. 입력값 상세 명세

## 5.1 생년월일

| 항목 | 내용 |
|---|---|
| 필드명 | birth_date |
| 화면 표시명 | 생년월일 |
| 타입 | date |
| 필수 여부 | 필수 |
| 예시 | 1999-03-14 |
| 기본값 | 없음 |
| 검증 규칙 | 비어 있으면 안 됨 |
| 오류 메시지 | 생년월일을 입력해 주세요. |

생년월일은 사주 기반 분석의 기본 입력값입니다.

MVP에서는 생년월일을 기반으로 간단한 사주 성향 또는 현재 상태 분석을 수행합니다.  
전문 만세력 수준의 정확한 사주 계산을 목표로 하지 않으며, 결과는 재미와 참고용으로 제공합니다.

## 5.2 출생 시간

| 항목 | 내용 |
|---|---|
| 필드명 | birth_time_branch |
| 화면 표시명 | 출생 시간 |
| 타입 | select |
| 필수 여부 | 선택 |
| 예시 | 신시 |
| 기본값 | 모름 |
| 검증 규칙 | 출생 시간 모름을 선택하면 birth_time_unknown을 true로 처리 |
| 오류 메시지 | 없음 |

출생 시간은 한국에서 일반적으로 사용하는 만세력 기준 12지시 시간표를 기준으로 입력받습니다.

MVP에서는 사용자가 정확한 시각을 직접 입력하는 방식이 아니라, 화면에서 “자시”, “축시”, “인시”처럼 12지시 구간을 선택하도록 합니다.

이 방식의 장점은 다음과 같습니다.

1. 사주 서비스 문맥에 맞는 입력 방식이다.
2. 사용자가 자신의 출생 시간이 어느 구간에 해당하는지 쉽게 선택할 수 있다.
3. 개발 시 시간 변환 로직을 단순화할 수 있다.
4. LLM 또는 Agent에 `birth_time_branch` 값을 그대로 전달하기 쉽다.
5. MVP 범위에서 복잡한 만세력 계산 로직보다 Agent Workflow와 추천 흐름 구현에 집중할 수 있다.

## 5.2.2 자시 처리 기준

자시는 하루의 경계에 걸쳐 있는 시간대입니다.

만세력 기준으로 자시는 다음과 같이 처리합니다.

| 구간 | 처리 기준 |
|---|---|
| 전날 23:30 ~ 23:59 | 자시 |
| 당일 00:00 ~ 01:30 | 자시 |

MVP에서는 사용자가 직접 “자시”를 선택하도록 하므로, 시스템이 날짜를 자동으로 전날 또는 당일로 보정하는 로직은 구현하지 않습니다.

다만 사주 분석 프롬프트 또는 Agent 입력에는 다음 정보를 함께 전달합니다.

| 필드 | 예시 |
|---|---|
| birth_date | 1999-03-14 |
| birth_time_branch | 자시 |
| birth_time_note | 자시는 전날 23:30 ~ 당일 01:30 구간입니다. MVP에서는 사용자가 선택한 생년월일을 기준으로 참고용 분석을 수행합니다. |

이렇게 처리하는 이유는 MVP에서 정확한 만세력 계산보다 사용자 입력 기반 Agent Workflow와 여행 추천 흐름 구현이 더 중요하기 때문입니다.

정확한 일자 보정, 절기 기준 계산, 음력 변환, 만세력 계산은 P1 또는 향후 고도화 범위로 분리합니다.

## 5.2.3 출생 시간 모름 처리

사용자가 “출생 시간 모름”을 선택한 경우 다음과 같이 처리합니다.

| 항목 | 처리 방식 |
|---|---|
| birth_time_branch | UNKNOWN |
| birth_time_unknown | true |
| 사주 분석 | 생년월일 중심으로 간단 분석 |
| 여행 스타일 매핑 | 출생 시간이 없다는 점을 고려해 과도한 단정 없이 스타일 도출 |
| 결과 안내 | 출생 시간이 없어 일부 해석이 단순화될 수 있음을 표시 |

안내 문구 예시:

출생 시간을 모르는 경우 일부 해석이 단순화될 수 있습니다.  
이 추천은 사주 기반 해석을 활용한 재미와 참고용 결과입니다.

## 5.3 양력/음력

| 항목 | 내용 |
|---|---|
| 필드명 | calendar_type |
| 화면 표시명 | 양력/음력 |
| 타입 | select |
| 필수 여부 | 필수 |
| 선택지 | 양력, 음력 |
| 기본값 | 양력 |
| 검증 규칙 | 반드시 하나를 선택해야 함 |
| 오류 메시지 | 양력 또는 음력을 선택해 주세요. |

MVP에서는 양력 기준 처리를 우선합니다.

음력 변환은 구현 부담이 있을 수 있으므로, 팀 상황에 따라 아래 중 하나로 처리합니다.

| 방식 | 설명 | 권장 여부 |
|---|---|---|
| 양력만 지원 | MVP에서는 양력만 선택 가능하게 함 | 가장 권장 |
| 음력 선택 시 안내 | 음력을 선택하면 양력 기준 분석으로 진행한다고 안내 | 가능 |
| 음력 변환 구현 | 변환 라이브러리를 사용해 양력으로 변환 | 시간이 남을 때 |

권장 MVP 방식:

- 화면에서는 양력만 우선 지원한다.
- 음력은 P1 또는 향후 고도화 범위로 둔다.

안내 문구 예시:

현재 MVP에서는 양력 기준 분석을 우선 제공합니다.

| 대구 | 대구 출발 기준 |

단, 여행지 데이터 작성 시간이 부족할 경우 서울 출발 기준을 우선 지원합니다.

권장 MVP 방식:

- 1차 데모에서는 서울 출발 기준 데이터를 우선 준비한다.
- 팀원이 여유가 있으면 대전 기준 데이터를 추가한다.
- 출발 지역을 많이 늘리기보다 여행지 추천 흐름이 안정적으로 동작하는 것을 우선한다.

안내 문구 예시:

현재 데모에서는 일부 출발 지역 기준 추천을 우선 제공합니다.

## 5.5 이동 가능 범위

| 항목 | 내용 |
|---|---|
| 필드명 | travel_range |
| 화면 표시명 | 이동 가능 범위 |
| 타입 | select |
| 필수 여부 | 필수 |
| 예시 | 3시간 이내 |
| 기본값 | 3시간 이내 |
| 검증 규칙 | 반드시 하나를 선택해야 함 |
| 오류 메시지 | 이동 가능 범위를 선택해 주세요. |

선택지는 다음과 같습니다.

| 값 | 내부 기준 |
|---|---:|
| 1시간 이내 | 1.0 |
| 2시간 이내 | 2.0 |
| 3시간 이내 | 3.0 |
| 전국 | 99.0 |

여행지 데이터의 distance_hours 값이 사용자의 travel_range 이하인 경우 후보로 포함합니다.

예시:

| 사용자 선택 | 여행지 이동 시간 | 처리 |
|---|---:|---|
| 3시간 이내 | 2.5 | 후보 포함 |
| 2시간 이내 | 2.5 | 후보 제외 또는 조건 완화 시 포함 |
| 전국 | 4.5 | 후보 포함 |

## 5.6 여행 기간

| 항목 | 내용 |
|---|---|
| 필드명 | duration |
| 화면 표시명 | 여행 기간 |
| 타입 | select |
| 필수 여부 | 필수 |
| 선택지 | 당일, 1박2일 |
| 기본값 | 1박2일 |
| 검증 규칙 | 반드시 하나를 선택해야 함 |
| 오류 메시지 | 여행 기간을 선택해 주세요. |

여행지 데이터의 available_duration에 사용자가 선택한 duration이 포함되어 있으면 후보로 포함합니다.

MVP에서는 당일과 1박2일만 지원합니다.

2박3일 이상은 이번 MVP에서 제외합니다.

## 5.7 선호 태그

| 항목 | 내용 |
|---|---|
| 필드명 | preference_tags |

선택지는 너무 많으면 사용자가 부담을 느낄 수 있으므로 MVP에서는 8개 내외로 제한합니다.

권장 선택지:

선호 태그는 필수값이 아니며, 선택한 경우 추천 점수에 가산점으로 반영합니다.

## 7. 여행 스타일 명세

## 7.1 여행 스타일 정의

MVP에서는 사주 분석 결과를 다음 6개 여행 스타일 중 하나로 변환합니다.

복잡도를 낮추기 위해 primary_style 하나를 필수로 반환하고, secondary_style은 선택값으로 둡니다.

| 스타일 ID | 여행 스타일 | 사용자 니즈 | 추천 방향 |
|---|---|---|---|
| STYLE_01 | 감정 회복형 | 지친 감정을 정리하고 안정감을 얻고 싶음 | 바다, 숲, 산책, 조용한 장소 |
| STYLE_02 | 에너지 충전형 | 답답함을 풀고 활력을 얻고 싶음 | 맛집, 핫플, 축제, 활기 있는 장소 |
| STYLE_03 | 인간관계 환기형 | 사람들과 분위기를 전환하고 싶음 | 카페거리, 시장, 야경, 도시 산책 |
| STYLE_04 | 자기 성찰형 | 혼자 생각을 정리하고 싶음 | 사찰, 한옥, 책방, 호수 |
| STYLE_05 | 액티비티 중심형 | 몸을 움직이며 스트레스를 풀고 싶음 | 레저, 트레킹, 서핑, 체험 활동 |
| STYLE_06 | 문화 탐방형 | 새로운 취향과 자극을 얻고 싶음 | 전시, 역사, 예술, 로컬 문화 |

## 7.2 여행 스타일 매핑 원칙

사주 분석 결과를 여행 스타일로 매핑할 때 다음 원칙을 사용합니다.

1. 사주 분석 결과에서 나온 키워드를 기반으로 스타일을 선택한다.
2. 스타일은 반드시 6개 중 하나를 primary_style로 선택한다.
3. 두 가지 성향이 함께 나타날 경우 secondary_style을 선택할 수 있다.
4. 여행 스타일은 여행지 데이터의 style_tags와 매칭된다.
5. 스타일 이름은 사용자에게 그대로 노출되므로 너무 추상적이지 않아야 한다.
6. 운세처럼 단정하지 않고 “이런 여행이 어울릴 수 있다”는 표현을 사용한다.

## 7.3 스타일 매핑 예시

| 분석 키워드 | primary_style |
|---|---|
| 회복, 안정, 정리, 휴식 | 감정 회복형 |
| 활력, 전환, 자극, 에너지 | 에너지 충전형 |
| 관계, 소통, 분위기 전환 | 인간관계 환기형 |
| 내면, 혼자, 정리, 집중 | 자기 성찰형 |
| 활동, 도전, 움직임, 스트레스 해소 | 액티비티 중심형 |
| 취향, 예술, 역사, 배움 | 문화 탐방형 |

## 7.4 스타일 출력값

여행 스타일 매핑 결과는 다음 값을 반환합니다.

| 필드명 | 설명 | 예시 |
|---|---|---|
| primary_style | 가장 강하게 추천되는 여행 스타일 | 감정 회복형 |
| secondary_style | 보조 여행 스타일 | 자기 성찰형 |
| style_keywords | 스타일 도출 키워드 | 회복, 안정, 산책 |
| style_reason | 스타일 도출 이유 | 최근에는 지친 감정을 정리하고 안정감을 회복하는 여행이 어울립니다. |

secondary_style은 선택값입니다.  
MVP에서는 primary_style만으로도 추천이 가능해야 합니다.

## 8. 여행지 추천 기능 명세

## 8.1 추천 방식 개요

여행지 추천은 LLM이 임의로 여행지를 생성하는 방식이 아닙니다.

MVP에서는 미리 정의된 여행지 데이터에서 후보 여행지를 찾고, 점수 기준에 따라 Top3를 선정합니다.

LLM은 최종 선정된 여행지에 대해 사용자에게 보여줄 추천 이유를 생성하는 역할을 담당합니다.

추천 흐름은 다음과 같습니다.

1. 여행지 데이터 로딩
2. 이동 가능 범위 기준 필터링
3. 여행 기간 기준 필터링
4. 여행 스타일 태그 기준 점수 계산
5. 사용자 선호 태그 기준 점수 계산
6. 추천 활동 데이터 존재 여부 반영
7. 총점 기준 내림차순 정렬
8. 상위 3개 여행지 선정
9. 추천 이유 생성

## 8.2 여행지 후보 필터링 기준

| 기준 | 설명 | MVP 필수 여부 |
|---|---|---|
| 이동 가능 범위 | distance_hours가 travel_range 이하인지 확인 | 필수 |
| 여행 기간 | available_duration에 duration이 포함되는지 확인 | 필수 |
| 여행 스타일 | style_tags에 primary_style 또는 secondary_style이 포함되는지 확인 | 권장 |
| 선호 태그 | place_tags와 preference_tags의 교집합 확인 | 선택 |
| 출발 지역 | departure_region 기준 이동 시간 사용 | 선택 |

MVP에서는 출발 지역별 정확한 이동 시간을 모두 계산하기 어렵기 때문에, 우선 서울 출발 기준 데이터를 준비하고 필요 시 대전 기준 데이터를 추가합니다.

출발 지역별 데이터가 부족한 경우 화면에 다음 문구를 표시합니다.

현재 데모에서는 일부 출발 지역 기준 추천을 우선 제공합니다.

## 8.3 후보 부족 시 처리

필터링 결과 후보가 3개 미만인 경우 다음 순서로 조건을 완화합니다.

| 순서 | 완화 방식 | 설명 |
|---:|---|---|
| 1 | secondary_style 포함 | primary_style만 보던 것을 secondary_style까지 확장 |
| 2 | 선호 태그 조건 제거 | preference_tags를 점수에서만 사용하고 필터에서는 제외 |
| 3 | 이동 범위 1단계 완화 | 2시간 이내면 3시간 이내로 완화 |
| 4 | 여행 기간 조건 완화 | 당일/1박2일 모두 가능한 후보 포함 |
| 5 | 기본 추천 후보 사용 | 그래도 부족하면 기본 후보 사용 |

후보 부족 안내 문구:

입력하신 조건에 정확히 맞는 여행지가 부족하여 일부 조건을 완화해 추천했습니다.

## 9. 추천 점수 기준

## 9.1 기본 점수 구조

추천 점수는 100점 기준으로 계산합니다.

| 기준 | 점수 | 설명 |
|---|---:|---|
| 여행 스타일 태그 일치 | 50점 | 여행지 style_tags와 사용자 여행 스타일 일치 |
| 이동 가능 범위 충족 | 20점 | distance_hours가 travel_range 이내 |
| 여행 기간 일치 | 15점 | available_duration에 사용자 duration 포함 |
| 사용자 선호 태그 일치 | 10점 | preference_tags와 place_tags 일치 |
| 추천 활동 데이터 존재 | 5점 | activities가 2개 이상 존재 |
| 총점 | 100점 | 최종 추천 점수 |

## 9.2 세부 점수 기준

### 9.2.1 여행 스타일 태그 일치

| 조건 | 점수 |
|---|---:|
| primary_style이 style_tags에 포함 | 50 |
| secondary_style이 style_tags에 포함 | 35 |
| 스타일은 다르지만 place_tags가 관련 있음 | 20 |
| 관련 없음 | 0 |

### 9.2.2 이동 가능 범위 충족

| 조건 | 점수 |
|---|---:|
| distance_hours가 travel_range 이내 | 20 |
| travel_range를 1단계 완화하면 포함 가능 | 10 |
| 이동 범위를 초과 | 0 |

### 9.2.3 여행 기간 일치

| 조건 | 점수 |
|---|---:|
| available_duration에 사용자 duration 포함 | 15 |
| 기간 정보가 없지만 추천 가능 | 5 |
| 기간이 맞지 않음 | 0 |

### 9.2.4 사용자 선호 태그 일치

| 조건 | 점수 |
|---|---:|
| 선호 태그 2개 이상 일치 | 10 |
| 선호 태그 1개 일치 | 5 |
| 선호 태그 미선택 | 5 |
| 일치 없음 | 0 |

선호 태그를 선택하지 않은 사용자가 불리해지지 않도록, 선호 태그 미선택 시 기본 5점을 부여합니다.

### 9.2.5 추천 활동 데이터 존재

| 조건 | 점수 |
|---|---:|
| activities 3개 이상 | 5 |
| activities 2개 | 3 |
| activities 1개 | 1 |
| activities 없음 | 0 |

## 9.3 최종 정렬 기준

후보 여행지는 다음 기준으로 정렬합니다.

1. 총점 높은 순
2. 총점이 같으면 primary_style 일치 여부 우선
3. 그래도 같으면 이동 시간이 짧은 순
4. 그래도 같으면 activities 개수가 많은 순
5. 그래도 같으면 데이터 순서 기준

      "recommendations": [
        {
          "rank": 1,
          "name": "강릉",
          "region": "강원",

## 11. 결과 화면 명세

## 11.1 결과 화면 목적

결과 화면은 사용자가 자신의 여행 스타일과 추천 여행지를 직관적으로 확인할 수 있도록 구성합니다.

## 11.2 결과 화면 구성 요소

| 순서 | 요소 | 설명 |
|---:|---|---|
| 1 | 분석 완료 메시지 | 추천 결과가 생성되었음을 안내 |
| 2 | 사용자 여행 스타일 | primary_style, secondary_style 표시 |
| 3 | 스타일 설명 | style_reason 표시 |
| 4 | 추천 여행지 카드 1 | 1순위 여행지 표시 |
| 5 | 추천 여행지 카드 2 | 2순위 여행지 표시 |
| 6 | 추천 여행지 카드 3 | 3순위 여행지 표시 |
| 7 | 추천 활동 | 각 여행지별 activities 표시 |
| 8 | 면책 문구 | 재미와 참고용 안내 |

## 11.3 결과 카드 구성

각 추천 여행지 카드는 다음 정보를 포함합니다.

| 항목 | 설명 |
|---|---|
| 순위 | 1위, 2위, 3위 |
| 여행지 이름 | 예: 강릉 |
| 지역 | 예: 강원 |
| 추천 점수 | 예: 92점 |
| 추천 이유 | 사용자 스타일과 연결된 자연어 설명 |
| 추천 활동 | 2~3개 활동 |
| 관련 태그 | 바다, 카페, 산책 등 |

## 11.4 결과 화면 면책 문구

결과 화면 하단에는 다음 문구를 항상 표시합니다.

이 추천은 사주 기반 해석을 활용한 재미와 참고용 결과입니다.  
실제 여행 결정은 개인 일정, 예산, 날씨, 교통 상황 등을 함께 고려해 주세요.

## 12. LLM 사용 범위

## 12.1 LLM을 사용하는 기능

MVP에서 LLM은 다음 기능에 사용합니다.

| 기능 | LLM 역할 |
|---|---|
| 사주 기반 간단 분석 | 생년월일과 출생 시간 정보를 바탕으로 현재 상태 또는 필요한 기운을 해석 |
| 여행 스타일 매핑 | 분석 결과를 여행 스타일 키워드로 변환 |
| 추천 이유 생성 | 선정된 여행지에 대한 자연어 추천 이유 작성 |

## 12.2 LLM을 사용하지 않는 기능

다음 기능은 LLM이 아니라 코드 로직으로 처리합니다.

| 기능 | 처리 방식 |
|---|---|
| 입력값 검증 | 코드 로직 |
| 여행지 데이터 로딩 | 코드 로직 |
| 이동 범위 필터링 | 코드 로직 |
| 여행 기간 필터링 | 코드 로직 |
| 추천 점수 계산 | 코드 로직 |
| Top3 선정 | 코드 로직 |
| 결과 카드 렌더링 | Streamlit 화면 구성 |

## 12.3 LLM 사용 원칙

LLM 사용 원칙은 다음과 같습니다.

1. LLM이 존재하지 않는 여행지를 임의로 생성하지 않도록 한다.
2. 여행지 후보와 활동 정보는 시스템이 전달한 데이터 안에서만 사용하게 한다.
3. 추천 이유는 과도하게 운세처럼 단정하지 않는다.
4. 의료, 재물, 연애, 합격, 건강 등 민감한 조언은 생성하지 않는다.
5. 결과는 재미와 참고용이라는 문구를 자연스럽게 포함한다.
6. 가능하면 화면 렌더링이 쉬운 구조로 응답하게 한다.

입력값 누락이 있는 경우 사주 분석과 추천 로직을 실행하지 않습니다.

## 13.2 출생 시간 모름

| 상황 | 처리 |
|---|---|
| 사용자가 출생 시간 모름 선택 | 생년월일 중심으로 간단 분석 |
| 결과 화면 | 정확도가 낮을 수 있다는 안내 표시 |

안내 문구:

출생 시간을 모르는 경우 일부 해석이 단순화될 수 있습니다.

## 13.3 여행지 후보 부족

| 상황 | 처리 |
|---|---|
| 후보가 3개 이상 | 정상 추천 |
| 후보가 1~2개 | 조건 완화 후 재검색 |
| 후보가 0개 | 기본 후보 또는 이동 범위 완화 추천 |

안내 문구:

입력하신 조건에 정확히 맞는 여행지가 부족하여 일부 조건을 완화해 추천했습니다.

## 13.4 LLM 응답 실패

| 상황 | 처리 |
|---|---|
| API 호출 실패 | 기본 템플릿 추천 이유 사용 |
| 응답 파싱 실패 | 기본 템플릿 추천 이유 사용 |
| 응답이 너무 길거나 형식이 깨짐 | 필요한 필드만 추출하거나 기본 문구 사용 |

기본 추천 이유 템플릿:

{여행지명}은 {여행스타일}에 어울리는 태그와 활동을 가진 여행지입니다.  
{추천활동}을 통해 현재 여행 목적에 맞는 시간을 보낼 수 있습니다.

## 13.5 여행지 데이터 로딩 실패

| 상황 | 처리 |
|---|---|
| 파일 없음 | 여행지 데이터를 불러올 수 없습니다. 표시 |
| JSON 또는 CSV 형식 오류 | 데이터 형식을 확인해 주세요. 표시 |
| 필수 필드 누락 | 해당 데이터를 제외하거나 기본값 처리 |

## 13.6 운세 단정 요청

사용자가 다음과 같은 요청을 하는 경우 정중히 제한합니다.

- 연애운을 단정해 주세요.
- 돈을 벌 수 있는 여행지를 알려주세요.
- 건강이 좋아지는 여행지를 알려주세요.
- 합격운이 좋아지는 곳을 알려주세요.

응답 방향:

이 서비스는 전문 운세 상담이 아니라 여행 추천을 위한 재미와 참고용 서비스입니다.  
대신 현재 입력값을 바탕으로 어울리는 여행 스타일과 여행지를 추천해드릴게요.

## 19. 요약

이번 MVP의 핵심 기능은 다음과 같습니다.

1. 사용자가 생년월일과 12지시 기반 출생 시간을 입력한다.
2. 사용자가 출발 지역, 이동 가능 범위, 여행 기간, 선호 태그를 입력한다.
3. 시스템이 입력값을 검증한다.
4. 사주 기반으로 현재 상태를 간단히 분석한다.
5. 분석 결과를 6개 여행 스타일 중 하나로 변환한다.
6. 여행지 데이터에서 조건에 맞는 후보를 찾는다.
7. 추천 점수를 계산해 Top3를 선정한다.
8. LLM으로 추천 이유를 생성한다.
9. 결과를 카드 형태로 출력한다.
10. 재미와 참고용 서비스임을 안내한다.

이 기능명세서는 개발자가 구현할 기준을 제공하는 문서입니다.  
상세 Agent 구조는 03_agent_workflow.md, 여행지 데이터 구조는 04_data_schema.md, 일정과 역할 관리는 05_wbs.md에서 관리합니다.
