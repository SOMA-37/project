# 04. 여행지 데이터 스키마

# 사주 기반 국내 여행지 추천 Agent MVP 데이터 스키마

## 1. 문서 목적

이 문서는 사주 기반 국내 여행지 추천 Agent MVP에서 사용할 여행지 데이터 구조를 정의하는 문서입니다.

이번 프로젝트의 추천 방식은 LLM이 여행지를 임의로 생성하는 방식이 아닙니다.

MVP에서는 미리 정리한 여행지 데이터에서 사용자의 조건에 맞는 후보를 찾고, 추천 점수 기준에 따라 Top3 여행지를 선정합니다.  
LLM은 선정된 여행지에 대해 추천 이유를 자연어로 작성하는 역할을 담당합니다.

따라서 여행지 데이터는 추천 품질과 데모 안정성에 직접적인 영향을 줍니다.

이 문서의 목적은 다음과 같습니다.

1. 여행지 데이터를 어떤 파일로 관리할지 정의한다.
2. 각 여행지 데이터가 어떤 필드를 가져야 하는지 정의한다.
3. 여행 스타일 태그와 장소 태그의 기준을 정의한다.
4. 개발자가 필터링과 점수 계산을 구현할 수 있도록 데이터 구조를 명확히 한다.
5. 기획/문서화 담당자가 여행지 데이터를 작성할 때 기준으로 사용할 수 있게 한다.
6. 발표에서 “데이터 기반 추천”이라고 설명할 수 있도록 추천 데이터 구조를 정리한다.

## 2. 데이터 관리 방식

## 2.1 MVP 기준 데이터 파일

MVP에서는 여행지 데이터를 JSON 또는 CSV 파일로 관리합니다.

권장 방식은 JSON입니다.

| 방식 | 장점 | 단점 | 권장 여부 |
|---|---|---|---|
| JSON | 배열, 태그, 활동 리스트 관리가 쉬움 | 사람이 대량 편집하기에는 CSV보다 불편할 수 있음 | 권장 |
| CSV | 엑셀이나 스프레드시트로 편집하기 쉬움 | 태그 배열, 활동 배열 관리가 불편함 | 가능 |
| DB | 확장성이 좋음 | MVP 기간 대비 구현 부담이 큼 | 제외 |

MVP에서는 별도 DB를 사용하지 않고, 프로젝트 내부의 정적 데이터 파일을 사용합니다.

권장 파일 경로:

    data/destinations.json

보조 샘플 파일:

    data/destinations.sample.json

## 3. 데이터 설계 원칙

여행지 데이터는 다음 원칙으로 작성합니다.

1. 추천 후보는 반드시 데이터 파일에 존재하는 여행지만 사용한다.
2. LLM이 새로운 여행지를 임의로 생성하지 않도록 한다.
3. 각 여행지는 최소한의 필수 필드를 가져야 한다.
4. 여행 스타일 매칭을 위해 style_tags를 반드시 작성한다.
5. 사용자 선호 태그 매칭을 위해 place_tags를 작성한다.
6. 결과 카드 출력을 위해 activities를 최소 2개 이상 작성한다.
7. MVP에서는 데이터 개수를 무리하게 늘리기보다, 추천 흐름이 안정적으로 동작하는 구조를 우선한다.
8. 5월 10일 데모 제출 전까지 최소 15개 이상의 여행지 데이터를 준비한다.
9. 5월 14일 최종 제출 전까지 가능하면 30개 내외로 확장한다.

## 4. 데이터 파일 구조

## 4.1 최상위 구조

destinations.json 파일은 여행지 객체의 배열 형태로 관리합니다.

예시 구조:

    [
      {
        "id": 1,
        "name": "강릉",
        "region": "강원",
        "departure_region": "서울",
        "distance_hours": 2.5,
        "available_duration": ["당일", "1박2일"],
        "style_tags": ["감정 회복형"],
        "place_tags": ["바다", "카페", "산책"],
        "activities": ["안목해변 산책", "카페거리 방문", "경포대 둘러보기"],
        "short_description": "바다와 카페를 중심으로 가볍게 회복하기 좋은 여행지"
      }
    ]

## 5. 여행지 데이터 필드 정의

## 5.1 전체 필드 목록

| 필드명 | 타입 | 필수 여부 | 예시 | 설명 |
|---|---|---|---|---|
| id | number | 필수 | 1 | 여행지 고유 ID |
| name | string | 필수 | 강릉 | 여행지 이름 |
| region | string | 필수 | 강원 | 여행지가 속한 지역 |
| departure_region | string | 권장 | 서울 | 이동 시간 기준 출발 지역 |
| distance_hours | number | 필수 | 2.5 | 출발 지역 기준 예상 이동 시간 |
| available_duration | string[] | 필수 | 당일, 1박2일 | 추천 가능한 여행 기간 |
| style_tags | string[] | 필수 | 감정 회복형 | 여행 스타일 태그 |
| place_tags | string[] | 필수 | 바다, 카페, 산책 | 장소 특성 태그 |
| activities | string[] | 필수 | 안목해변 산책, 카페거리 방문 | 추천 활동 |
| short_description | string | 필수 | 바다와 카페를 중심으로 회복하기 좋은 여행지 | 여행지 간단 설명 |
| recommendation_note | string | 선택 | 조용한 회복 여행에 적합 | 추천 참고 메모 |
| image_keyword | string | 선택 | 강릉 바다 | 이미지 검색 또는 발표자료용 키워드 |

MVP에서는 필수 필드만 있어도 동작 가능해야 합니다.

선택 필드는 발표자료나 결과 카드 품질을 높이기 위해 사용할 수 있습니다.

## 6. 필드별 상세 설명

## 6.1 id

| 항목 | 내용 |
|---|---|
| 필드명 | id |
| 타입 | number |
| 필수 여부 | 필수 |

작성 기준:

- 숫자로 작성합니다.
- 중복되면 안 됩니다.
- 데이터 순서가 바뀌어도 여행지를 구분할 수 있어야 합니다.

예시:

    "id": 1

## 6.2 name

| 항목 | 내용 |
|---|---|
| 필드명 | name |
| 타입 | string |
| 필수 여부 | 필수 |
| 예시 | 강릉 |

여행지 이름입니다.

작성 기준:

- 사용자에게 그대로 노출될 수 있는 이름으로 작성합니다.
- 너무 넓은 이름보다 실제 여행지로 인식 가능한 이름을 사용합니다.
- 도시 단위 또는 대표 지역 단위로 작성합니다.

좋은 예시:

- 강릉
- 전주
- 가평
- 속초
- 경주

피해야 할 예시:

- 바다 여행
- 힐링 장소
- 강원도 어딘가
- 좋은 곳

| 항목 | 내용 |
|---|---|
| 필드명 | region |
| 타입 | string |
| 필수 여부 | 필수 |

권장 값:

## 6.4 departure_region

| 항목 | 내용 |
|---|---|
| 필드명 | departure_region |
| 타입 | string |
| 필수 여부 | 권장 |
| 예시 | 서울 |

이동 시간의 기준이 되는 출발 지역입니다.

MVP에서는 출발 지역별 정확한 이동 시간을 모두 관리하기 어렵기 때문에, 우선 서울 출발 기준 데이터를 작성하는 것을 권장합니다.

추가 여유가 있으면 대전 출발 기준 데이터를 일부 추가할 수 있습니다.

작성 기준:

- 1차 MVP: 서울 기준 우선
- 시간이 남으면 대전 기준 추가
- 여러 출발 지역을 지원하려면 같은 여행지를 출발 지역별로 별도 데이터로 작성할 수 있음

예시:

    {
      "id": 1,
      "name": "강릉",
      "departure_region": "서울",
      "distance_hours": 2.5
    }

같은 여행지를 대전 기준으로도 관리하려면 다음처럼 별도 ID로 작성할 수 있습니다.

    {
      "id": 101,
      "name": "강릉",
      "departure_region": "대전",
      "distance_hours": 3.5
    }

다만 MVP에서는 데이터 중복 관리가 부담될 수 있으므로, 우선 서울 기준으로 통일하는 것을 권장합니다.

## 6.5 distance_hours

| 항목 | 내용 |
|---|---|
| 필드명 | distance_hours |
| 타입 | number |
| 필수 여부 | 필수 |
| 예시 | 2.5 |

출발 지역 기준 예상 이동 시간입니다.

작성 기준:

- 시간 단위 숫자로 작성합니다.
- 2시간 30분은 2.5로 작성합니다.
- 1시간 30분은 1.5로 작성합니다.
- 정확한 실시간 교통 시간이 아니라, MVP 추천 필터링을 위한 대략적인 이동 시간입니다.

사용 방식:

| 사용자 선택 | 내부 기준 | 포함 조건 |
|---|---:|---|
| 1시간 이내 | 1.0 | distance_hours <= 1.0 |
| 2시간 이내 | 2.0 | distance_hours <= 2.0 |
| 3시간 이내 | 3.0 | distance_hours <= 3.0 |
| 전국 | 99.0 | 대부분 포함 |

주의사항:

- 실시간 교통 상황은 반영하지 않습니다.
- 대중교통과 자가용 시간을 엄밀하게 구분하지 않습니다.
- 발표 시 “MVP에서는 대략적인 이동 가능 범위를 기준으로 필터링했다”고 설명합니다.

## 6.6 available_duration

| 항목 | 내용 |
|---|---|
| 필드명 | available_duration |
| 타입 | string[] |
| 필수 여부 | 필수 |
| 예시 | ["당일", "1박2일"] |

해당 여행지가 어떤 여행 기간에 적합한지 나타냅니다.

허용 값:

| 값 | 설명 |
|---|---|
| 당일 | 당일치기 가능 |
| 1박2일 | 1박2일 여행 적합 |

작성 기준:

- 최소 1개 이상 작성합니다.
- 당일과 1박2일 모두 가능하면 둘 다 작성합니다.
- MVP에서는 2박3일 이상은 지원하지 않습니다.

예시:

    "available_duration": ["당일"]

    "available_duration": ["1박2일"]

    "available_duration": ["당일", "1박2일"]

## 6.7 style_tags

| 항목 | 내용 |
|---|---|
| 필드명 | style_tags |
| 타입 | string[] |
| 필수 여부 | 필수 |
| 예시 | ["감정 회복형", "자기 성찰형"] |

여행지와 연결되는 여행 스타일 태그입니다.

이 필드는 사주 분석 결과에서 도출된 여행 스타일과 매칭하는 데 사용됩니다.

허용 값:

| 값 | 설명 |
|---|---|
| 감정 회복형 | 지친 감정을 정리하고 안정감을 얻는 여행 |
| 에너지 충전형 | 답답함을 풀고 활력을 얻는 여행 |
| 인간관계 환기형 | 사람들과 분위기 전환을 하는 여행 |
| 자기 성찰형 | 혼자 생각을 정리하는 여행 |
| 액티비티 중심형 | 몸을 움직이며 스트레스를 푸는 여행 |
| 문화 탐방형 | 새로운 취향과 자극을 얻는 여행 |

작성 기준:

- 최소 1개 이상 작성합니다.
- 가능하면 1~3개 사이로 작성합니다.
- 너무 많은 스타일을 붙이면 추천 기준이 흐려지므로 지양합니다.
- 해당 여행지의 대표 경험과 가장 잘 맞는 스타일을 우선 작성합니다.

좋은 예시:

    "style_tags": ["감정 회복형", "자기 성찰형"]

    "style_tags": ["문화 탐방형"]

    "style_tags": ["에너지 충전형", "인간관계 환기형"]

피해야 할 예시:

    "style_tags": ["감정 회복형", "에너지 충전형", "인간관계 환기형", "자기 성찰형", "액티비티 중심형", "문화 탐방형"]

## 6.8 place_tags

| 항목 | 내용 |
|---|---|
| 필드명 | place_tags |
| 타입 | string[] |
| 필수 여부 | 필수 |
| 예시 | ["바다", "카페", "산책"] |

여행지의 장소 특성을 나타내는 태그입니다.

이 필드는 사용자 선호 태그와 매칭하는 데 사용됩니다.

MVP 권장 태그:

| 태그 | 설명 |
|---|---|
| 바다 | 바다, 해변, 항구 |
| 산/숲 | 산, 숲, 수목원, 자연휴양림 |
| 카페 | 카페거리, 감성 카페 |
| 맛집 | 음식, 시장, 지역 먹거리 |
| 전시/문화 | 전시, 박물관, 문화공간 |
| 산책 | 걷기 좋은 거리, 호수, 공원 |
| 야경 | 야경 명소, 밤 산책 |
| 액티비티 | 레저, 체험, 트레킹 |

작성 기준:

- 최소 2개 이상 작성합니다.
- 가능하면 3~5개 사이로 작성합니다.
- style_tags보다 구체적인 장소 특성을 적습니다.
- 사용자 입력의 preference_tags와 같은 용어를 사용합니다.

예시:

    "place_tags": ["바다", "카페", "산책"]

    "place_tags": ["전시/문화", "맛집", "산책"]

    "place_tags": ["산/숲", "액티비티", "산책"]

## 6.9 activities

| 항목 | 내용 |
|---|---|
| 필드명 | activities |
| 타입 | string[] |
| 필수 여부 | 필수 |
| 예시 | ["안목해변 산책", "카페거리 방문", "경포대 둘러보기"] |

추천 활동 목록입니다.

이 필드는 결과 카드에 표시되며, LLM이 추천 이유를 생성할 때도 사용합니다.

작성 기준:

- 최소 2개 이상 작성합니다.
- 가능하면 3개 작성합니다.
- 너무 긴 문장보다 짧은 활동명으로 작성합니다.
- 실제 여행자가 할 수 있는 활동이어야 합니다.

좋은 예시:

    "activities": ["안목해변 산책", "카페거리 방문", "경포대 둘러보기"]

    "activities": ["한옥마을 산책", "전통 음식 체험", "경기전 방문"]

피해야 할 예시:

    "activities": ["힐링하기"]

    "activities": ["좋은 시간 보내기"]

## 6.10 short_description

| 항목 | 내용 |
|---|---|
| 필드명 | short_description |
| 타입 | string |
| 필수 여부 | 필수 |
| 예시 | 바다와 카페를 중심으로 가볍게 회복하기 좋은 여행지 |

여행지의 간단한 설명입니다.

이 설명은 다음 용도로 사용됩니다.

1. 개발 중 데이터 확인
2. 결과 카드 보조 설명
3. LLM 추천 이유 생성 참고 정보
4. 발표자료 작성 시 여행지 설명

작성 기준:

- 한 문장으로 작성합니다.
- 30~80자 정도를 권장합니다.
- 여행지의 핵심 특징이 드러나야 합니다.
- 과장된 표현은 피합니다.

예시:

    "short_description": "바다와 카페를 중심으로 가볍게 회복하기 좋은 여행지"

## 6.11 recommendation_note

| 항목 | 내용 |
|---|---|
| 필드명 | recommendation_note |
| 타입 | string |
| 필수 여부 | 선택 |
| 예시 | 조용한 회복 여행을 원하는 사용자에게 적합 |

기획자가 추천 의도를 메모하기 위한 선택 필드입니다.

MVP 구현에는 필수는 아니지만, LLM 추천 이유 생성이나 발표자료 준비에 도움이 될 수 있습니다.

## 6.12 image_keyword

| 항목 | 내용 |
|---|---|
| 필드명 | image_keyword |
| 타입 | string |
| 필수 여부 | 선택 |

이미지 검색, 발표자료 제작, 결과 카드 확장 시 사용할 수 있는 키워드입니다.

MVP에서는 필수 구현하지 않습니다.

## 8. 데이터 작성 기준

## 8.1 최소 데이터 개수

MVP 기준 데이터 개수는 다음과 같이 관리합니다.

| 시점 | 목표 개수 | 설명 |
|---|---:|---|
| 5/10 데모 제출 | 최소 15개 | 추천 흐름 동작 확인용 |
| 5/14 프로젝트 제출 | 가능하면 30개 내외 | 추천 다양성 확보 |
| 향후 고도화 | 50개 이상 | 지역/스타일별 추천 품질 개선 |

5월 10일 데모 제출 전에는 데이터 개수보다 전체 추천 흐름이 동작하는 것이 더 중요합니다.

따라서 15개 정도의 데이터라도 스타일과 태그가 잘 분산되어 있으면 충분히 데모가 가능합니다.

## 8.2 스타일 분포 기준

여행 스타일별 데이터가 너무 한쪽으로 몰리지 않도록 작성합니다.

최소 권장 분포:

| 여행 스타일 | 최소 데이터 수 |
|---|---:|
| 감정 회복형 | 3개 이상 |
| 에너지 충전형 | 2개 이상 |
| 인간관계 환기형 | 2개 이상 |
| 자기 성찰형 | 2개 이상 |
| 액티비티 중심형 | 2개 이상 |
| 문화 탐방형 | 2개 이상 |

하나의 여행지가 여러 style_tags를 가질 수 있으므로, 실제 여행지 개수는 15개 내외여도 스타일 커버가 가능합니다.

## 8.3 지역 분포 기준

MVP에서는 지역 다양성보다 추천 흐름 안정성을 우선합니다.

권장 지역 구성:

| 지역 | 권장 개수 |
|---|---:|
| 수도권/근교 | 4~6개 |
| 강원 | 3~5개 |
| 충청 | 2~4개 |
| 전라 | 2~4개 |
| 경상 | 2~4개 |
| 제주 | 선택 |

서울 출발 기준으로 이동 시간이 너무 긴 여행지가 많으면 데모에서 필터링 결과가 부족할 수 있으므로, 3시간 이내 여행지를 충분히 포함합니다.

## 8.4 이동 시간 분포 기준

travel_range 필터가 정상 동작하려면 이동 시간 분포도 필요합니다.

권장 분포:

| 이동 시간 | 권장 데이터 수 |
|---|---:|
| 1시간 이내 | 2개 이상 |
| 2시간 이내 | 4개 이상 |
| 3시간 이내 | 6개 이상 |
| 3시간 초과 | 3개 이상 |

이렇게 작성하면 사용자가 1시간, 2시간, 3시간, 전국 중 무엇을 선택해도 추천 결과가 나올 가능성이 높아집니다.

## 8.5 여행 기간 분포 기준

여행 기간은 당일과 1박2일을 지원합니다.

권장 작성 방식:

| 여행 기간 | 설명 |
|---|---|
| 당일 | 가까운 지역, 짧은 산책, 카페, 전시 중심 |
| 1박2일 | 이동 시간이 긴 지역, 바다, 역사, 자연 여행 중심 |
| 당일 + 1박2일 | 둘 다 가능한 지역 |

데모 안정성을 위해 많은 여행지에 ["당일", "1박2일"]을 함께 부여해도 됩니다.

단, 제주처럼 현실적으로 당일치기가 어려운 여행지는 1박2일만 부여합니다.

| 오류 상황 | 처리 방식 |

| id 중복 | 데이터 수정 필요 |
| style_tags 값 오류 | 추천 점수 계산에서 제외될 수 있음 |
| distance_hours 누락 | 필터링 불가하므로 제외 |
| activities 없음 | 추천 활동 점수 0점 처리 |

## 12. 여행 스타일별 데이터 작성 예시

## 12.1 감정 회복형

- 바다
- 숲

- 조용한 산책
- 카페
- 혼자 가도 부담 없는 장소

- 함께 걷기 좋은 거리

- 시장
- 도시 산책
- 친구와 대화하기 좋은 장소

- 조용한 산책

| 필드 | 값 |

## 14. 데이터 작성 시 주의사항

## 14.1 너무 많은 태그를 붙이지 않는다

하나의 여행지에 너무 많은 style_tags를 붙이면 추천 기준이 흐려집니다.

나쁜 예시:

    "style_tags": ["감정 회복형", "에너지 충전형", "인간관계 환기형", "자기 성찰형", "액티비티 중심형", "문화 탐방형"]

좋은 예시:

    "style_tags": ["감정 회복형", "자기 성찰형"]

## 14.2 활동은 실제로 할 수 있는 것으로 작성한다

나쁜 예시:

    "activities": ["힐링하기", "재밌게 놀기"]

좋은 예시:

    "activities": ["안목해변 산책", "카페거리 방문", "경포대 둘러보기"]

## 14.3 LLM이 새 정보를 만들지 않도록 데이터에 필요한 정보를 넣는다

추천 이유 생성 시 LLM이 없는 정보를 만들어내지 않도록, 최소한 다음 정보는 데이터에 넣어야 합니다.

- 여행지 이름
- 장소 태그
- 추천 활동
- 간단 설명

## 14.4 출발 지역을 무리하게 늘리지 않는다

출발 지역별 이동 시간을 정확히 관리하려면 데이터 작업량이 크게 늘어납니다.

MVP에서는 서울 출발 기준을 우선하고, 필요하면 대전 기준 일부 데이터만 추가합니다.

## 14.5 실시간 정보처럼 보이게 작성하지 않는다

MVP 데이터는 정적 데이터입니다.

따라서 다음과 같은 표현은 피합니다.

- 오늘 가장 인기 있는
- 현재 가장 저렴한
- 실시간으로 사람이 많은
- 이번 주 날씨가 좋은

대신 다음처럼 작성합니다.

- 바다 산책을 즐기기 좋은
- 전통 문화와 음식을 함께 경험할 수 있는
- 서울 근교에서 가볍게 다녀오기 좋은

## 15. CSV로 관리할 경우

JSON 대신 CSV로 관리할 경우 다음 컬럼을 사용합니다.

| 컬럼명 | 설명 |
|---|---|
| id | 여행지 ID |
| name | 여행지 이름 |
| region | 지역 |
| departure_region | 출발 지역 |
| distance_hours | 이동 시간 |
| available_duration | 당일;1박2일 |
| style_tags | 감정 회복형;자기 성찰형 |
| place_tags | 바다;카페;산책 |
| activities | 안목해변 산책;카페거리 방문;경포대 둘러보기 |
| short_description | 간단 설명 |
| recommendation_note | 추천 메모 |
| image_keyword | 이미지 키워드 |

CSV에서는 배열 값을 세미콜론으로 구분합니다.

예시:

| id | name | region | departure_region | distance_hours | available_duration | style_tags | place_tags |
|---:|---|---|---|---:|---|---|---|
| 1 | 강릉 | 강원 | 서울 | 2.5 | 당일;1박2일 | 감정 회복형;자기 성찰형 | 바다;카페;산책 |

개발 시 CSV를 읽은 뒤 세미콜론을 기준으로 배열로 변환합니다.

예시 변환 규칙:

| 원본 값 | 변환 결과 |
|---|---|
| 감정 회복형;자기 성찰형 | ["감정 회복형", "자기 성찰형"] |
| 바다;카페;산책 | ["바다", "카페", "산책"] |
| 안목해변 산책;카페거리 방문 | ["안목해변 산책", "카페거리 방문"] |

## 16. 데이터 검수 체크리스트

여행지 데이터를 작성한 뒤 아래 항목을 확인합니다.

## 16.1 필수 체크

- [ ] id가 중복되지 않는다.
- [ ] name이 비어 있지 않다.
- [ ] region이 작성되어 있다.
- [ ] distance_hours가 숫자로 작성되어 있다.
- [ ] available_duration이 1개 이상 작성되어 있다.
- [ ] style_tags가 1개 이상 작성되어 있다.
- [ ] place_tags가 2개 이상 작성되어 있다.
- [ ] activities가 2개 이상 작성되어 있다.
- [ ] short_description이 작성되어 있다.

## 16.2 추천 품질 체크

- [ ] 감정 회복형 여행지가 3개 이상 있다.
- [ ] 에너지 충전형 여행지가 2개 이상 있다.
- [ ] 인간관계 환기형 여행지가 2개 이상 있다.
- [ ] 자기 성찰형 여행지가 2개 이상 있다.
- [ ] 액티비티 중심형 여행지가 2개 이상 있다.
- [ ] 문화 탐방형 여행지가 2개 이상 있다.
- [ ] 3시간 이내 여행지가 충분히 있다.
- [ ] 당일 여행 가능한 여행지가 충분히 있다.
- [ ] 1박2일 여행 가능한 여행지가 충분히 있다.

## 16.3 데모 체크

- [ ] 정상 시나리오에서 Top3가 출력된다.
- [ ] 후보 부족 시 조건 완화가 동작한다.
- [ ] 추천 이유 생성에 필요한 activities가 존재한다.
- [ ] 결과 카드에 표시할 name, region, activities가 모두 있다.
- [ ] LLM이 새 여행지를 만들지 않아도 추천 이유를 작성할 수 있다.

## 17. 개발 구현 시 사용 예시

## 17.1 데이터 로딩

개발자는 destinations.json을 로딩해 여행지 목록을 배열로 사용합니다.

처리 흐름:

    1. destinations.json 파일을 읽는다.
    2. JSON 배열을 Python list로 변환한다.
    3. 각 여행지 객체의 필수 필드를 검증한다.
    4. 유효한 데이터만 추천 로직에 전달한다.

## 17.2 후보 필터링

필터링 기준:

    distance_hours <= travel_range
    duration in available_duration

추가적으로 style_tags와 place_tags는 점수 계산에 활용합니다.

## 17.3 추천 점수 계산

각 여행지마다 score를 계산합니다.

score 계산에 사용하는 필드:

    style_tags
    distance_hours
    available_duration
    place_tags
    activities

계산 결과는 여행지 객체에 score 필드를 추가해 관리할 수 있습니다.

예시:

    {
      "id": 1,
      "name": "강릉",
      "score": 100
    }

## 17.4 결과 카드 출력

결과 카드에는 다음 필드를 사용합니다.

| 화면 요소 | 데이터 필드 |
|---|---|
| 여행지 이름 | name |
| 지역 | region |
| 추천 점수 | score |
| 추천 이유 | reason |
| 추천 활동 | activities |
| 관련 태그 | place_tags |

## 19. 향후 확장 방향

MVP 이후 데이터 구조는 다음 방향으로 확장할 수 있습니다.

## 19.1 계절 태그 추가

예시 필드:

    "season_tags": ["봄", "가을"]

활용:

- 봄에 어울리는 여행지
- 여름 바다 여행
- 가을 단풍 여행
- 겨울 온천 여행

## 19.2 동행 유형 추가

예시 필드:

    "companion_tags": ["혼자", "친구", "연인", "가족"]

활용:

- 혼자 가기 좋은 여행
- 친구와 가기 좋은 여행
- 가족과 가기 좋은 여행

## 19.3 예산 태그 추가

예시 필드:

    "budget_level": "중간"

활용:

- 저예산 여행
- 적당한 비용의 여행
- 프리미엄 여행

## 19.4 지도 링크 추가

예시 필드:

    "map_url": "https://map.example.com"

활용:

- 결과 카드에서 지도 바로가기 제공
- 실제 여행 행동으로 연결

## 19.5 RAG 적용을 위한 설명 필드 확장

예시 필드:

    "detailed_description": "강릉은 동해 바다와 카페 문화가 발달한 지역으로..."

활용:

- 여행지 설명 임베딩
- 의미 기반 검색
- 사용자 상태와 여행지 설명 매칭

## 20. 요약

이번 MVP의 여행지 데이터는 추천 로직의 기준이 되는 핵심 자원입니다.

데이터 작성의 핵심은 다음과 같습니다.

1. 여행지는 JSON 또는 CSV로 관리한다.
2. MVP에서는 JSON을 권장한다.
3. 추천 후보는 반드시 데이터에 존재하는 여행지만 사용한다.
4. style_tags는 사주 분석 결과와 여행 스타일을 연결하는 핵심 필드다.
5. place_tags는 사용자 선호 태그와 연결되는 필드다.
6. activities는 결과 카드와 LLM 추천 이유 생성에 사용된다.
7. distance_hours와 available_duration은 필터링에 사용된다.
8. 5월 10일 데모 제출 전까지 최소 15개 데이터를 준비한다.
9. 5월 14일 프로젝트 제출 전까지 가능하면 30개 내외로 확장한다.
10. 데이터 개수보다 스타일, 태그, 이동 시간 분포가 더 중요하다.

이 문서는 여행지 데이터 작성과 개발 구현의 기준 문서입니다.
